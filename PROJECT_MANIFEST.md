## 📊 Database Changes

### New Fields on Order Table
```
Total (DECIMAL(18,2))
├── Stores: Total amount paid by customer
├── Why: Prices change over time, need historical record
└── Example: 99.99

ShippingAddress (NVARCHAR(500))
├── Stores: Full delivery address
├── Why: Customers move after ordering
└── Example: "123 Main St, New York, NY 10001"

PaymentMethod (NVARCHAR(50))
├── Stores: How customer paid
├── Why: Track payment methods for analytics/disputes
└── Example: "CreditCard", "BankTransfer"

PaymentDate (DATETIME2)
├── Stores: When payment was confirmed
├── Why: CreatedAt ≠ PaymentDate
└── Example: 2025-11-27 10:05:30
```

### Data Model
```
AppUser (1:Many) Order (1:Many) OrderProduct (Many:1) Product
```

## 💡 Design Decisions

### 1. Service Pattern
**Decision:** Separate business logic from HTTP handling  
**Benefit:** Reusability, testability, maintainability

### 2. DTOs
**Decision:** Transfer data with DTOs, not database models  
**Benefit:** Security, flexibility, type safety

### 3. Transactions
**Decision:** All-or-nothing database operations  
**Benefit:** Data consistency, no corrupted orders

### 4. Server-Side Calculations
**Decision:** Calculate totals on server, never client  
**Benefit:** Security, unhackable prices

### 5. User Verification
**Decision:** Check `UserId` on every query  
**Benefit:** Users can only see own orders
